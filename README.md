# Pontifex

**A verified bridge from Python to Lean 4.**

Pontifex translates a restricted Python subset through a typed SSA IR into Lean 4,
where the kernel checks the translation and its control-flow refinement.

Write a small numerical routine in Python. `pontifex` translates it through a
typed SSA intermediate representation into Lean 4, and checks in the kernel
that

1. the emitted IR **body** is exactly the body produced by a reference SSA
   lowering, and
2. the emitted Lean code is equivalent to the IR semantics —
   *for every fuel budget and every arithmetic backend* when control flow is
   involved, including failures and exhaustion.

The first application is a physics integrator, but the pipeline is generic.
The verified core is built on **Lean core only**: no Mathlib, no `ring` tactic,
no `sorry`, no `native_decide` in certificates.

---

## Verification at a glance

| Claim | Status |
| --- | --- |
| Emitted IR body = reference SSA lowering of the emitted core AST | **Kernel-checked** per program (`<fn>_lowering := rfl`) |
| Straight-line Lean code = IR semantics | **Kernel-checked** at a literal fuel (`<fn>_link := rfl`) |
| `if` / `while` code = IR semantics | **Kernel-checked for all fuel, inputs, and `Ops α`**, preserving returned / fellThrough / failed / stuck / outOfFuel |
| More fuel preserves completed observations | **Proved** (`exec_mono`, `exec_completed_stable`) |
| Total correctness implies partial correctness | **Proved** (`total_to_partial`) |
| Symplectic Euler preserves its modified energy | **Proved** (`symplecticStep_modifiedEnergy`) |
| Free-fall position after `n` steps | **Proved** (`repeatStep_position_twice`) |
| Translation of Python source to the core AST | **Trusted + tested**, not proved |
| Array reads, updates, and `len` | **Kernel-checked** per program; bad/out-of-range index is `failed .indexOutOfBounds` |
| Bounded white-box helper calls | **Kernel-checked** expansion plus compositional per-callee lowering evidence |
| `min`/`max` and scalar conditional expressions | **Kernel-checked** all-fuel/all-backend linkage; eager operands / lazy branches |
| Native binary64/CPU arithmetic | **Tested bit-for-bit**, not proved |
| Native Python numeric tower and exceptions | **Out of scope** |

Every certificate is replayed by `lake build` and audited for axioms. Only
Lean's standard logical axioms (`propext`, `Classical.choice`, `Quot.sound`) are
allowed; `sorryAx`, native-evaluation trust hooks, and project-specific axioms
fail the build.

## The pipeline

### 1 · Python source
A single function in the verified subset: scalar parameters, assignments,
`if`/`else`, `while`, and tuple `return`s, including early exits from a branch
or a loop body.

```python
def step(x: float, v: float, a: float, dt: float):
    v = v + a * dt
    x = x + v * dt
    return x, v
```

### 2 · Core AST
`ast.parse` and strict subset validation, followed by purely syntactic
desugaring: augmented assignment, `**` with a literal natural exponent,
`abs`, unary minus, and removal of docstrings/`pass`. Variables become
integer ids assigned in sorted name order, so “sorted assigned names” becomes
“sorted ids” in the proved lowering.

### 3 · SSA IR
A structured, explicitly typed IR with slot ids, `phi` merges, and loop-carried
header slots. Every assignment writes a fresh slot. Literals are exact
rationals; Float literals retain their exact binary value *and* original bits.
The canonical IR is also serialized as JSON, versioned by an exact schema
number.

An IR sequence stops at the first `returned` outcome, so a branch that always
returns never reaches an `if` merge or a loop back edge. Merge slots come only
from the branches that can still fall through; the returning side of a phi is a
dead but defined slot. The frontend rejects unreachable statements after a
definitely-returning statement, functions that can fall through without
returning, and returns that disagree on arity.

Slots hold tagged values (`Val α = .scalar α | .array (List α)`), so an array
flows through the same phis and loop headers as a scalar. Array length is
intrinsic; `xs[i]` and `xs[i] = v` are bounds-checked, and the update is a
functional expression assigned to a fresh slot (no aliasing, no separate array
environment).

### 4 · Lean code
Two emission paths, both kernel-linked to the IR:

* **Infallible straight-line code** becomes a direct functional definition over
  `Rat`, linked by `rfl`.
* **Control flow or fallible arithmetic** becomes independently emitted
  slot-state blocks with an explicit outcome algebra. Blocks never call the IR
  interpreter; each gets a certificate, loops are proved by induction on fuel,
  and the public theorem quantifies over every fuel, environment, and
  arithmetic backend.

### 5 · Proofs and specifications
An independent physics specification (free fall, harmonic oscillator, clamping)
is linked to the generated code. The core-only proof toolkit includes a
certified polynomial normalizer (`rat_ring`), a proof driver
(`pontifex_step`), and total/partial spec wrappers over the outcome order.

## Quick start

```bash
uv sync                        # Python tooling (pytest, hypothesis, pillow)
lake build                     # Lean library, generated examples, axiom audit, runner
make check                     # freshness + audit + corpora + full test suite

python scripts/generate.py     # regenerate Pontifex/Generated/*.lean + audit
make corpus                    # CPython ↔ IR ↔ Lean differential corpus
make float-boundaries          # 100k binary64 patterns + IEEE edge cases
make rejections                # refresh rejection diagnostics after review
```

Translate and inspect a function:

```bash
uv run python -m pontifex ir    examples/free_fall.py
uv run python -m pontifex emit  examples/free_fall.py
uv run python -m pontifex eval  examples/free_fall.py --args 1,2,3,4
uv run python -m pontifex eval  examples/free_fall.py --args=-0.0 --float
uv run python -m pontifex compile examples/free_fall.py \
    --out /tmp/FreeFall.lean --json /tmp/ff.json --with-samples
```

The Lean oracle used by differential tests:

```bash
lake exe pontifex rat   build/ir/free_fall.json inputs.json
lake exe pontifex float build/ir/free_fall.json inputs.json
```

Float inputs are `"0x<hex bits>"`; rationals are `"n"` or `"n/d"`.

## What the kernel actually checks

For each generated module:

```lean
-- the emitted IR body is the reference lowering of the emitted core AST
theorem step_lowering :
    Source.lowerBody stepSource = .ok stepIR.body := rfl

-- straight-line code is definitionally the IR semantics
theorem step_link (x v a dt : Rat) :
    step 64 x v a dt =
      (Outcome.toOption (Fn.run Ops.rat stepIR 64 [x, v, a, dt]))
        .map (fun vs => (vs[0]!, vs[1]!)) := rfl
```

For control flow and fallible arithmetic:

```lean
theorem simulate_compiled_link (ops : Ops α) [Inhabited α]
    (fuel : Nat) (args : List α) :
    simulateCompiled ops fuel args = Fn.run ops simulateIR fuel args
```

and the public wrapper is linked at every fuel. The emitted blocks preserve
`returned`, `fellThrough`, `failed`, `stuck`, and `outOfFuel`, so fuel
monotonicity and partial-correctness statements can be derived without
re-proving the translation.

### Proved with the core-only normalizer

```lean
theorem symplecticStep_modifiedEnergy (omega2 dt x v : Rat) :
    modifiedEnergy omega2 dt (symplecticStep omega2 dt ⟨x, v⟩) =
      modifiedEnergy omega2 dt ⟨x, v⟩ := by
  simp only [modifiedEnergy, symplecticStep]
  rat_ring

theorem repeatStep_position_twice (n : Nat) (a dt x v : Rat) :
    2 * (repeatStep n a dt ⟨x, v⟩).x =
      2*x + 2*(n:Rat)*v*dt + a*dt*dt*(n:Rat)*((n:Rat)+1)
```

`rat_ring` reifies both sides, normalizes integer-coefficient polynomials with
kernel-reducible `Int`/list operations, and emits a checked equality chain. It
handles coefficient arithmetic and cancellation; rational literal coefficients
must be cleared first.

### Proving properties of generated code

`pontifex_step` unfolds the semantics, splits symbolic branches, and finishes
with local decision procedures:

```lean
example (x v a dt : Rat) :
    (Generated.FreeFall.step 64 x v a dt).map Prod.snd =
      some (v + a * dt) := by
  pontifex_step [Generated.FreeFall.step]
```

See [`docs/STEP_TACTIC.md`](docs/STEP_TACTIC.md).

## Trust boundary

Kernel proofs start at the **emitted core AST**. The following remain trusted or
tested, and are documented in [`docs/TRUST.md`](docs/TRUST.md):

* `ast.parse`, subset checking, surface desugaring, and transcription of the AST
  into the emitted `Source` literal;
* fidelity of the Lean reference lowering to Python semantics (the lowering is a
  formal executable specification; `<fn>_lowering` proves agreement with it, not
  semantic preservation for all Python programs);
* native `Float`/CPU arithmetic and `Float.ofBits`/`toBits` behavior — exercised
  bit-for-bit by the boundary corpus, not proved correct;
* Python's full numeric tower, evaluation-order effects outside the modeled
  expression fragment, and the exception hierarchy beyond the modeled failures.

The differential harness (`CPython ↔ IR interpreter ↔ Lean oracle`) is the
mitigation for this boundary; it is not a substitute for a source-semantics
proof, and the docs say so explicitly.

## Outcomes, fuel, and numerics

`Outcome α` is

```text
returned values | fellThrough env | failed Error | stuck | outOfFuel
```

* Failures (`divisionByZero`, Float power `overflow`) and `stuck` are **stable
  completed observations**. Only exhaustion is incomplete.
* `Outcome.Refines a b := a = outOfFuel ∨ a = b` is a flat partial order with
  bottom (not a lattice): distinct results have no common upper bound.
* Fuel is structured execution depth: sequence head/tail, selected branch, and
  loop body/back edge each receive one less level. It is not a global
  instruction counter. Exhaustion is not a divergence proof.
* Uninitialized slots and phi predecessors are `stuck`; gaps are never
  manufactured as zero.

Two numeric readings are explicit:

| Backend | Meaning |
| --- | --- |
| `Ops.rat` | exact rational arithmetic, the mathematical reading (not the full real field) |
| `Ops.float` | Lean's built-in native `Float` model |
| `Ops.binary64` | raw-bit wire/literal tier plus a native Float value tier; used by the oracle's `float` mode |

Float literals carry their exact binary value and original bits, so subnormals,
signed zero, infinities, and NaN payloads survive identity transport. Division
checks both zero signs; `**` is a backend operation, not a multiplication
expansion. See [`docs/FLOAT_POLICY.md`](docs/FLOAT_POLICY.md) for the exact
policy, the two-tier `FloatSpec` lemmas, and the computed-NaN allowlist.

## Supported Python subset (v0)

One function per module, or an explicitly selected entry point (`--function`)
with module-local helpers; scalar parameters, and:

* statements: `x = e`, `x: T = e`, `x += e` (`-=`, `*=`, `/=`), `if`/`else`,
  `while`, `pass`, `return` of scalars (early returns allowed; every path must
  return the same number of values);
* expressions: names, int/float literals, `+ - * /`, `**` with an integer literal
  exponent in `[0, 8]`, unary `-`, `abs(x)`, eager two-positional-argument
  `min(a, b)`/`max(a, b)`, and lazy scalar `a if condition else b`. Ties/unordered
  comparisons keep the first `min`/`max` operand, including signed zero and NaN
  payloads. See [`docs/SELECTION.md`](docs/SELECTION.md);
* conditions: one comparison at a time, `and` / `or` / `not`, booleans;
* arrays: one-dimensional list literals `[a, b, c]`, bounds-checked reads
  `xs[i]`, functional updates `xs[i] = v`, and `len(xs)`. Arrays are values in
  tagged slots: an update writes a fresh array slot, so there is no aliasing.
  Array parameters, array returns, nested arrays, and augmented subscript
  assignment are rejected. A bad index (fractional, negative) and an
  out-of-range integer index both produce `failed .indexOutOfBounds`;
* bounded white-box calls: `x = helper(...)`, `x: T = helper(...)`,
  `return helper(...)`, or a helper call inside a scalar expression (operands,
  arguments, array elements/indices, store values, return tuples), with
  positional scalar arguments and straight-line, single-scalar helpers
  (including acyclic helper chains). Caller control flow remains supported.
  Expression calls are hoisted in evaluation order; a call may not follow a
  failing operand in the same statement, and calls inside conditions or
  conditional-expression branches are rejected. Callee control flow,
  tuple/array results, keyword/starred calls, and recursion are deferred. See
  [`docs/CALLS.md`](docs/CALLS.md) for the boundary and compositional certificates.

Everything else is rejected with a located, snapshotted diagnostic — no imports,
`for`, `break`/`continue`, `try`, `with`, lambdas, comprehensions, attribute
access, iterable/variadic/keyword `min`/`max`, array-valued conditional
expressions, scalar truthiness, or tuple unpacking.

### Continuous integration

The workflows in `.github/workflows/` split the checks by domain so a failure
points at one layer:

| Workflow | Trigger | Checks |
| --- | --- | --- |
| `lean.yml` | push to `main`, PR | `lake build` (including the generated axiom audit) plus a full `leanchecker` kernel replay |
| `python.yml` | push to `main`, PR | `ruff format --check`, generated-artifact and rejection-snapshot freshness, and the full pytest suite on Python 3.10 and 3.13 |
| `corpus.yml` | push to `main`, PR | 32-program differential corpus and the 100,000-pattern binary64 boundary corpus |
| `nightly.yml` | daily 04:17 UTC | Re-runs all three with 256 corpus samples, 1,000,000 float patterns, and 32,768 arithmetic cases |

All workflows have read-only repository permissions and use the committed
`uv.lock` and `lean-toolchain` pins. `corpus.yml` and the domain workflows are
also reusable (`workflow_call`), which is how the nightly job requests larger
sample counts.

## Status and roadmap

**P0, P1, P2 complete.** The verified core now covers:

* per-program lowering and code↔IR certificates;
* control flow and fallible arithmetic with explicit outcomes;
* fuel refinement and total/partial specs;
* a certified integer-polynomial normalizer and two headline physics theorems;
* two-tier binary64 component specifications;
* build-time axiom, schema, rejection, corpus, and Float-boundary gates.

**P3 — language growth:** multi-exit returns and one-dimensional state vectors
with bounds failures are implemented, as are two-argument `min`/`max` and lazy
scalar conditional expressions (schema 4). Function calls are in progress:
bounded white-box scalar helpers inline with compositional certificates,
including expression-position calls hoisted in evaluation order; callee control
flow and summaries remain open. Next are an opacity lattice
with a verified-path assertion and the Python integer/numeric-tower decision.

**Research:** a recursively verified source semantics/frontend, native IEEE
arithmetic proofs, rational-coefficient normalization, and a CFG-first IR with
a verified structuring pass.

Tracked as GitHub issues: [epic #15](https://github.com/michaelnavazhylau/pontifex/issues/15)

## Related work

The pipeline is deliberately Aeneas-shaped. [`docs/RELATED_WORK.md`](docs/RELATED_WORK.md)
reviews [Charon](https://github.com/AeneasVerif/charon) and
[Aeneas](https://github.com/AeneasVerif/aeneas) and records what was borrowed:

* explicit IR serialization with schema/version stamping (implemented);
* outcome orders and total/partial spec readings (implemented);
* a rule-driven proof driver (implemented);
* committed negative tests and a differential corpus (implemented);
* structured-vs-unstructured control flow, a fallible representation of
  unsupported constructs, and an opacity lattice (design direction, not yet
  implemented).

The main deliberate divergence: Aeneas trusts its translator and relies on
typechecking plus proof replay, whereas `pontifex` emits a **per-program kernel
certificate** for its small language.
